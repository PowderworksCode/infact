## Resolved-destination allocation (clone/to_owned by receiver type)

State on 08-02: WORKING AND TESTED, NOTHING COMMITTED. Read the transfer
section at the bottom FIRST — most of this exists only in a working tree.

The question was whether the MIR provider could supply the receiver types that
`clone` and `to_owned` need. It can, but not as it was written, and the change
that makes it work also breaks something silently. All three parts below are
one change; landing part 1 without part 2 is a regression that reports success.

### What was measured, so nobody re-derives it

Probed the driver against a fixture of clone/to_owned/collect/format calls.

  BEFORE. Every clone collapses to one destination:
    clone_an_arc     -> std::clone::Clone::clone
    clone_a_string   -> std::clone::Clone::clone
    clone_a_vec      -> std::clone::Clone::clone
    own_a_str        -> std::borrow::ToOwned::to_owned
    own_an_integer   -> std::borrow::ToOwned::to_owned
  The receiver is discarded at the `RigidTy::FnDef(def, _)` match — the `_` is
  the generic args, which is where `Self` lives — and `def.0.name()` names the
  trait method rather than the impl. `coverage.types` is false and `types` is
  empty; that part is honest and unchanged.

  AFTER `Instance::resolve(def, &args)`:
    <std::sync::Arc<std::string::String> as std::clone::Clone>::clone
    <std::string::String as std::clone::Clone>::clone
    std::str::<impl std::borrow::ToOwned for str>::to_owned
    <i32 as std::borrow::ToOwned>::to_owned
    <Copied<Iter<'_, u8>> as Iterator>::collect::<std::vec::Vec<u8>>
    std::vec::Vec::<u8>::with_capacity
    std::fmt::format
  More than asked for: `collect`'s TARGET container is in the name, and
  `format!` arrives as an ordinary resolved call to `std::fmt::format`.

  `i32::clone` emits NO call terminator at all — inlined away. Do not rely on
  that to filter Copy types: `i32::to_owned` DOES emit one.

### The trap, and it is the important part

Resolution rewrites `std::fs::read` to `std::fs::read::<&str>`. Every catalog
lookup is an exact map `get`, so all of them stop matching. Measured: with the
regenerated fixture and no other change, 5 of 6 `observed` tests failed with
empty effect sets while the run still reported `EffectResolution::Observed`.
The one test that PASSED was `a_pure_function_reports_no_effect`. A confident,
empty answer is the worst failure this codebase can produce, and it is what
part 1 alone produces.

### Two parsing traps found the hard way, both now regression-tested

  `::<impl Trait for Type>` opens exactly like a turbofish. Stripping it as one
  discards the receiver — the single thing the resolved destination was wanted
  for. `path::without_turbofish` special-cases it.

  A resolved `collect` arrives QUALIFIED (`<Iter as Iterator>::collect::<..>`),
  so a `collect` branch written in the unqualified arm never fires. Order
  matters in `allocating_destination`: check `collect` before the qualified-self
  branch.

### Decided, with the reason, so it is not relitigated

  The seed's `origin` records the DECLARED catalog path, not the resolved
  instance. Otherwise one catalogued API gets a different origin at every call
  site that instantiates it differently, which fragments any grouping a
  consumer does. `external_effect` returns the matched key for this.

  `clone`/`to_owned` are decided ONLY on the observed path. The syntax path
  still declines them outright and must keep doing so — it has no receiver
  type and a guess would put false origins in the one relation whose value is
  that it can be trusted.

  User types are declined for `clone`. A custom `Clone` may do anything.

  The name-based tables were kept as the fallback rather than replaced.
  `allocating_destination` defers to `allocating_call` for anything it cannot
  place, and the syntax path still needs them.

### Result, same seven functions through both paths

  syntax                          observed (MIR)
    collects_a_vec   collect        clones_a_string  String::clone      NEW
    collects_nothing collect  <-!   collects_a_vec   collect::<Vec>
    formats          format!        formats          std::fmt::format
                                    owns_a_str       str::to_owned      NEW
                                    (collects_nothing absent — correct)

  Two allocations that were invisible; one false positive gone
  (`Result<(), ()>` collects nothing); `Arc::clone` still correctly declined,
  which is the discrimination and not merely more hits.

## What to do next

[ ] THE REAL GAP: nothing generates observations in a normal workflow
    All of the above only applies when a repository HAS observations. Producing
    them means a build with `entl-rust-mir` standing in for rustc, and there is
    no one-command path to it. On a repo without observations the syntax path
    runs and NOTHING above changes. This is the highest-value next task by a
    wide margin — the capability is built and largely unreachable.
    Straitjacket already has an `observations` config key and a fixture using
    it; the missing piece is generating them, not consuming them.

[ ] Generic functions are skipped entirely
    `Instance::try_from(item)` fails for a non-monomorphic item, so the driver
    records a gap and moves on. Calls inside generic functions are NOT in the
    graph at all. In generic-heavy Rust this bounds observed coverage far more
    than anything in this note, and it is unrelated to the resolution change.
    Worth measuring before trusting observed coverage as complete.

[ ] Loop nesting depth
    Still nothing. `Form` already distinguishes Traverse/Transform/Retain/
    Accumulate, so the nesting depth of a call site is free and honest. Without
    it "allocates inside a loop" is not sayable and barriers stay
    callable-granular. This was the original recommendation and is still open.

[ ] One finding per (callable, effect)
    `evidence_path` returns a single path, so a callable allocating in twelve
    places surfaces them one re-run at a time.

[ ] A barrier configured but never marked is silent
    Mirror of `unknown-barrier`, which catches the marker-with-no-barrier case.
    Needs cross-file state a straitjacket FileRule does not have.

[ ] No `[[effects.barriers]]` is configured in any repo
    `effect-barrier` and `unknown-barrier` both ship working and inert. Nothing
    exercises them outside tests.

[ ] infact-normalize/src/lib.rs is OVER the file-size limit
    1756 lines against straitjacket's 1500. It is the one finding standing
    between infact and a clean policy run; entl and straitjacket are both
    clean. This is the supercompilation work, and `simplify.rs` looks like the
    extraction that resolves it — finishing that split closes the finding
    without anyone having to think about the rule.

      provenance digest are both DONE and verified; writing the queries is the
      remaining step. ~210 of the crate's 744 lines are recognition; the call
      graph and reach resolution stay Rust regardless.
