## infact-python-normalize exists, and it found two bugs in the shared core

Landed 08-04. A frontend onto `infact-normalize`, same shape as the TypeScript
one, ~1,100 lines of reader plus ~250 of form passes. It depends on the Python
parser pack (entl PR #13) and on nothing else new.

### What it canonicalizes, in the order that matters

  1. BUILDING A SEQUENCE. Python writes "make a new list from an old one" three
     ways and one of them is three statements:

         out = []                          [g(x) for x in xs if p(x)]
         for x in xs:                ==
             if p(x):
                 out.append(g(x))

     `fuse_container_fills` is the pass. This is Python's version of the rule
     that an index walk and a `for..of` are one traversal; without it the two
     commonest spellings of the same operation reduce to unrelated forms and
     nothing else in the crate is worth anything.
  2. FAILURE. `try`/`except` becomes a `Select` whose arms name the exception,
     which is the shape Rust's `match` on a `Result` already has. The type name
     is kept: recovering from a missing key is not recovering from a bad value.
  3. PRECONDITIONS. A guard that only raises, and `assert`, are dropped, exactly
     as the TypeScript frontend drops a throw-only guard.

DELIBERATELY NOT DONE: no builtin is folded into the loop it stands for. `sum`,
`sorted`, `max` stay ordinary calls. Rust and TypeScript recognize their
iteration METHODS because those take a closure whose body IS the behavior;
Python's builtins take a whole sequence and are opaque, and reducing them would
say a caller had reimplemented what it in fact called.

### Coverage, measured before claiming any

`--example coverage` over CPython `Lib` plus the installed site-packages —
7,680 files, 165,145 functions, 5.05M form nodes:

    opaque nodes   4,339   0.086% of form nodes
      while        4,323   deliberate: a `while` walks something unnamed
      reversed        16   deliberate: a backwards comprehension

That is ALL of it. Every accidental gap is closed; the only things the frontend
cannot read are the two it declines to guess at.

It did not start there. The first measurement was 15,620 opaque nodes (0.309%)
and RANKING them is what made it cheap to fix:

    slice              11,243   72% of everything unreadable -- `xs[1:2]`
    while               4,323
    line_continuation      14   a `\` shifting `comparison`'s positional read
    ==, <, is, <=          17   the same bug, handing an operator to `expression`

The slice rule also has to keep the bound the source left out, or `xs[1:]` and
`xs[:1]` — opposite halves — become one form.

### TWO BUGS IN infact-normalize, BOTH FOUND BY RUNNING ON REAL CODE

Neither is a Python bug. Both are in `simplify.rs`, both abort the process
rather than failing, and both are reachable from Rust and TypeScript the moment
a frontend binds a nested function to a name.

  1. UNFOLDING A NAME THAT CALLS ITSELF NEVER TERMINATES. `apply_bindings`
     replaces a call with the body it names and then recurses on the result; if
     the body calls back, each pass is strictly larger. CPython's
     `json/encoder.py` binds `_iterencode`, `_iterencode_list` and
     `_iterencode_dict` inside one factory with each calling the others. Fixed
     by `unfoldable()`, which keeps only the acyclic part of a binding group.

  2. A CYCLE CAN ARRIVE THROUGH AN ARGUMENT, where no analysis of the binding
     group can see it. The Y combinator is the shortest example and
     `Lib/test/test_inspect` writes one:

         def Y(le):
             def g(f):
                 return le(lambda x: f(f)(x))
             return g(g)

     `g` names nothing recursive; substituting `g` for `f` produces `f(f)`
     again. Fixed with fuel — `MAX_UNFOLDS` — rather than with more cleverness.

WHAT SAID IT WAS A CYCLE AND NOT DEPTH: a half-gigabyte stack did not help, and
then a full gigabyte did not either. Worth remembering as the cheapest test.

The fuel SPANS THE WHOLE `simplify()` CALL, not one pass. Per-pass it compounded:
eight sweeps each unfolding 64 levels deeper than the last left a form that was
bounded and still large enough to exhaust a debug build's stack when anything
walked it. Release passed and debug aborted, which is the worst way to find out.

[ ] MAX_UNFOLDS IS A TUNING KNOB AND HAS NOT BEEN TUNED. The first comment I
    wrote called it "a backstop rather than a tuning knob". That was wrong and
    the corpus said so: total form size over CPython's `Lib` keeps rising with
    every increase and never plateaus —

        4 -> 2,390,857 nodes    16 -> 2,418,798    64 -> 2,443,675

    Real bodies consume all of it, because unfolding into a body used twice
    makes the form bigger ON PURPOSE — that is how a caller's inlined shape
    comes to match a library's. So the value trades what a form says against how
    large it gets, and 64 is where the pathological cases were fixed, not a
    measured optimum. Calibrating it needs a matching corpus.

### The collision discipline, built alongside rather than after

`tests/collisions.rs` and `tests/fixtures/distinct.py` — 22 callables chosen so
every pair is close enough for a plausible erasure to collapse it. It cannot do
what the Rust one does (there is no Python behavior derivation and so no
receiver type to appeal to), so it also asserts the specific distinctions the
other frontends have each paid for once: forwards vs backwards, keys vs values,
map vs filter, counting vs summing, which exception, lazily vs gathered.

It found one erasure on its first run, and it was the same one the Rust frontend
had already paid for: a tuple literal reduced to `Construct("tuple")`, so `(a,
b)` and `(b, a)` were one form. THE COLLISION ASSERTION DID NOT CATCH IT — the
fixture held only one such callable. The size floor did, by reporting four nodes
for a function that plainly says more. Both are kept for that reason.

Empty collection literals still reduce to `Construct`, deliberately:
`fuse_container_fills` recognizes that shape, and it is what lets an append loop
be seen at all.

[ ] Behavior derivation and library matching are NOT here, per the night's
    scope. What they will need from this crate already exists: `LocatedForm`
    carries a span and a depth for every statement at every depth, which is what
    lets a match be reported at the line that carries it.
[ ] `while` is the one real gap. 4,323 opaque nodes, all of them a loop whose
    sequence the syntax does not name. TypeScript solved its own version by
    recognizing the counter; Python's `while` is genuinely unbounded more often,
    and guessing would turn every loop into the same traversal.

## Resolved-destination allocation (clone/to_owned by receiver type)

State on 08-02: WORKING AND TESTED, NOTHING COMMITTED. Read the transfer
section at the bottom FIRST — most of this exists only in a working tree.

The question was whether the MIR provider could supply the receiver types that
`clone` and `to_owned` need. It can, but not as it was written, and the change
that makes it work also breaks something silently. All three parts below are
one change; landing part 1 without part 2 is a regression that reports success.

### What was measured, so nobody re-derives it

Probed the driver against a fixture of clone/to_owned/collect/format calls.

  BEFORE. Every clone collapses to one destination:
    clone_an_arc     -> std::clone::Clone::clone
    clone_a_string   -> std::clone::Clone::clone
    clone_a_vec      -> std::clone::Clone::clone
    own_a_str        -> std::borrow::ToOwned::to_owned
    own_an_integer   -> std::borrow::ToOwned::to_owned
  The receiver is discarded at the `RigidTy::FnDef(def, _)` match — the `_` is
  the generic args, which is where `Self` lives — and `def.0.name()` names the
  trait method rather than the impl. `coverage.types` is false and `types` is
  empty; that part is honest and unchanged.

  AFTER `Instance::resolve(def, &args)`:
    <std::sync::Arc<std::string::String> as std::clone::Clone>::clone
    <std::string::String as std::clone::Clone>::clone
    std::str::<impl std::borrow::ToOwned for str>::to_owned
    <i32 as std::borrow::ToOwned>::to_owned
    <Copied<Iter<'_, u8>> as Iterator>::collect::<std::vec::Vec<u8>>
    std::vec::Vec::<u8>::with_capacity
    std::fmt::format
  More than asked for: `collect`'s TARGET container is in the name, and
  `format!` arrives as an ordinary resolved call to `std::fmt::format`.

  `i32::clone` emits NO call terminator at all — inlined away. Do not rely on
  that to filter Copy types: `i32::to_owned` DOES emit one.

### The trap, and it is the important part

Resolution rewrites `std::fs::read` to `std::fs::read::<&str>`. Every catalog
lookup is an exact map `get`, so all of them stop matching. Measured: with the
regenerated fixture and no other change, 5 of 6 `observed` tests failed with
empty effect sets while the run still reported `EffectResolution::Observed`.
The one test that PASSED was `a_pure_function_reports_no_effect`. A confident,
empty answer is the worst failure this codebase can produce, and it is what
part 1 alone produces.

### Two parsing traps found the hard way, both now regression-tested

  `::<impl Trait for Type>` opens exactly like a turbofish. Stripping it as one
  discards the receiver — the single thing the resolved destination was wanted
  for. `path::without_turbofish` special-cases it.

  A resolved `collect` arrives QUALIFIED (`<Iter as Iterator>::collect::<..>`),
  so a `collect` branch written in the unqualified arm never fires. Order
  matters in `allocating_destination`: check `collect` before the qualified-self
  branch.

### Decided, with the reason, so it is not relitigated

  The seed's `origin` records the DECLARED catalog path, not the resolved
  instance. Otherwise one catalogued API gets a different origin at every call
  site that instantiates it differently, which fragments any grouping a
  consumer does. `external_effect` returns the matched key for this.

  `clone`/`to_owned` are decided ONLY on the observed path. The syntax path
  still declines them outright and must keep doing so — it has no receiver
  type and a guess would put false origins in the one relation whose value is
  that it can be trusted.

  User types are declined for `clone`. A custom `Clone` may do anything.

  The name-based tables were kept as the fallback rather than replaced.
  `allocating_destination` defers to `allocating_call` for anything it cannot
  place, and the syntax path still needs them.

### Result, same seven functions through both paths

  syntax                          observed (MIR)
    collects_a_vec   collect        clones_a_string  String::clone      NEW
    collects_nothing collect  <-!   collects_a_vec   collect::<Vec>
    formats          format!        formats          std::fmt::format
                                    owns_a_str       str::to_owned      NEW
                                    (collects_nothing absent — correct)

  Two allocations that were invisible; one false positive gone
  (`Result<(), ()>` collects nothing); `Arc::clone` still correctly declined,
  which is the discrimination and not merely more hits.

## Behavior derivation — the algebra, decisions, and candidate sets

State on 08-02: WORKING AND TESTED, NOTHING COMMITTED. Separate thread from the
allocation work above; the two touch different crates and do not conflict.

The question was whether a library's behavior can be recognized in code that
reimplements it, for any library, without running anything. It can. `find` now
matches a hand-written loop, derived from std's source alone — no execution
anywhere in the pipeline, and rustc's own inliner and LLVM both fail to relate
those two, so this is not something a compiler was going to hand us.

### What was measured, so nobody re-derives it

Three corpora, all reproducible (commands at the bottom):

  std behaviors        290 -> 483    (a peak of 1,590 was mostly garbage; see below)
  clippy recall        0/201 -> 14/201, and 22 of 22 reported are on-target
  dependency corpus    34 -> 1,035 findings over 494 crates
  undecided matches    76 -> 64

The behavior count going DOWN from 1,590 to 483 was the point, not a loss. The
permissive gate admitted opaque `match` trees and `Arc`/`HashMap` methods
resolved to unrelated functions; removing them cost no recall on either corpus.

### The one idea

Each law is an equivalence that holds in the LANGUAGE, not in any library, so
one set serves every library there is. In crates/infact-normalize/src/simplify.rs:

  unfolding       a name bound to a body is that body
  traversal       a fold whose accumulator is unused is a traversal
  escape          breaking out of a fold is returning from a loop
  recovery        asking a fold for the value it broke with is that return
  generalization  a name nothing in the form binds is a hole
  fusion          mapping what was filtered is one pass, not two

These five unlocked NINE std methods at once — find, find_map, try_find, any,
all, position, for_each, try_for_each, partition — because all of them are
written with try_fold + ControlFlow. That is the evidence that the approach is
about the language and not about `find`.

Matching gained one rule of the same kind: a hole APPLIED to a bound name
matches any expression over that name (Miller pattern unification). That is
what lets a library's `predicate(item)` match a caller's `item == target`.

### The recurring bug, which is the important part

Eight distinct bugs this session were ONE pattern: a distinction erased in
normalization. Each produced hundreds to thousands of confidently wrong
findings, and none was visible in the output.

  true / ()                 both were Form::Literal. 1,390 false matches.
  map / filter_map          one TRANSFORM_METHODS list. map cannot drop.
  next / next_back          ranked by size, so the reverse iterator won.
  e.into() / e              stripped as noise. into_ok became into_err.
  Self                      read as a type name. 55 behaviors from non-bodies.
  (k, _) / (_, v)           `_` is anonymous, so the position was dropped.
                            BTreeMap::keys and ::values were one behavior.
  arm order                 `match` survived as syntax, so order was behavior.
  filename collisions       {package}-{leaf}.json. 23% of every pack overwritten.

FOUR of these were found by accident. The last four were found on purpose, by
crates/infact-rust-behaviors/tests/collisions.rs, which asserts that distinct
callables derive distinct forms. RUN THAT FIRST after any normalizer change.
It is the cheapest bug detector in the project.

3. LAZY-ADAPTOR DERIVATION. THE LIFT IS BUILT AND CORRECT. IT MOVED CLIPPY BY
   ZERO. That is the FIFTH misprediction in a row, and this time the laws were
   right and the reach was wrong again — read the warning below before doing
   anything with the rest of this item.

   BUILT 08-02, `Form::lifted_from_one_step` in infact-normalize/src/simplify.rs:
     core::Iterator::filter_map  ->  (sift f0 v1 (call f1 v1))
   exactly the form this item predicted. `find_map` correctly did NOT lift and
   keeps its search form, which resolved the filter_map/find_map collision
   (same-container collisions 10 -> 9). The lift is deliberately NOT a law and
   is not part of `simplify`: a search stops at the first hit and a lazy adaptor
   does not, so only derivation may apply it.

   The licence is STICKY, and this is the part that is easy to get wrong. The
   construction is followed at `filter_map -> next`, but the liftable form only
   appears one step LATER, at `next -> find_map` via ordinary delegation. A
   per-step flag reads false exactly where the lift is needed. Derivation tracks
   `inside_one_step` across the whole walk and lifts once at the end.

   The stateful guard is in and fails closed (`is_stateful_step`): refuses a
   step that assigns through a field or walks more than one sequence.

   WHY IT SCORED NOTHING, measured on one case rather than guessed. The two
   sides do not meet:

     library, after the lift   (sift f0 v1 (call f1 v1))
     user, .filter(p).map(f)   (collect (sift f0 v0 (branch COND (Some ..) (None))))
     user, the manual loop     does not reduce to a sift AT ALL — it stays
                               (do (let v0 (construct Vec))
                                   (traverse f0 v1 (select .. => (method push v0 v2)))
                                   v0)

   So fusion does produce a `Sift` from a chain, but its body is an explicit
   Option construction where the library's is a bare applied hole, and the whole
   thing sits under a `collect` the library form has no counterpart for. The
   claim in this note that `(sift f0 v1 (call f1 v1))` "matches BOTH
   .filter_map(f) and the fused .filter(p).map(f)" was hand-verified and is
   WRONG as measured: zero findings on the probe.

   THE BLOCKER IS `is_reportable`, AND IT IS NOT A BUG. Chased 08-02 and the
   first two guesses were both wrong; recorded so nobody re-walks them:

     WRONG GUESS 1: the `collect` wrapper. Disproved by probing the same chain
     WITHOUT a collect — `(sift f0 v0 (branch ..))` bare still does not match.
     `search` already recurses into children, so the wrapper was never in the
     way.
     WRONG GUESS 2: `(call HOLE item)` failing to match `(branch ..)`.
     `abstraction` implements exactly that (Miller unification) and none of its
     refusal conditions fire here.

   THE ACTUAL REASON. `is_reportable` demands `anchors >= 2` AND
   `anchors >= holes`. The lifted form is

       (sift f0 v1 (call f1 v1))     anchors 0, holes 2

   `Sift`, `Free`, `Call` and `Local` all contribute NO anchors. It names no
   type, no method, no operator, no constant — it is pure shape, and pure shape
   matches any code of that shape. That is the `Option::map_or` failure this
   codebase already paid for once: technically right, reported nine hundred
   times across five hundred crates, useless. Asserted now by
   `the_lifted_form_names_nothing` in simplify.rs so it is not rediscovered.

   NOTE THE TRADE. Before the lift, `filter_map` carried the big
   Sequence/Traverse/Select form, whose `Select` arms name `Some` and `None` and
   so DOES clear the anchor bar. The lift exchanged a reportable-but-ambiguous
   form (identical to `find_map`, so any match named the wrong API half the
   time) for an unambiguous-but-unreportable one. Neither scored: recall was
   14/201 before and after. Precision went up, reportability went to zero.

   SO THE ~63 POINTS ARE NOT REACHABLE THIS WAY AT ALL, and the reason is the
   one already written in "What NOT to spend time on" below. manual_filter_map,
   manual_find_map and filter_map_next are SHAPE lints, exactly like
   needless_range_loop and manual_while_let_some: `filter_map` names nothing, so
   "you could use filter_map" is a statement about shape and not about
   reimplementing a particular library function. Getting them requires weakening
   `anchors`, which exists for a measured reason. That is the same trade this
   note already declined once, and the ~63 belongs in the NOT-worth-it list
   rather than in this item's headline.

   WHAT THE LIFT IS STILL WORTH. It is correct, it is tested, and it resolved
   the filter_map/find_map collision. Keep it. Its value is precision, not
   recall, and this item should no longer be sold on a clippy number.

   ORIGINAL NOTE FOLLOWS, kept because the analysis of the lift itself held up.

   Phase 0 is DONE and the premise holds. A lazy
   adaptor's behavior derived from `next` is ONE-STEP semantics: FilterMap::next
   delegates to find_map, so what is stored under `filter_map` IS find_map. The
   lift is one rewrite — a terminal search is the lazy operation with a stop in
   it, so drop the stop:

     (do (traverse s x (select SCRUT (None) => (lit) (Some p) => (return (variant Some p)))) (variant None))
       -> Sift(s, x, SCRUT)
     (do (traverse s x (branch COND (return (variant Some x)))) (variant None))
       -> Retain(s, x, COND)

   Verified by hand that `(sift f0 v1 (call f1 v1))` then matches BOTH
   `.filter_map(f)` and the fused `.filter(p).map(f)`.

   License it only on the ONE branch in derivation.rs where a callable merely
   constructs a type and we follow into its principal method. That branch is now
   exactly the lazy-adaptor path — the `principal.then_some(..)` fix removed
   Arc and HashMap from it, so it needs no further guarding against them.

   Guard it against STATEFUL adaptors, failing closed: refuse when `next`
   mutates self fields, touches more than one sequence, or loops. Flatten,
   Peekable and Chunks must refuse; they do not derive today, so refusing costs
   nothing and admitting them would be undetectable downstream.

   Worth ~63 clippy points (manual_filter_map 29, manual_find_map 30,
   filter_map_next 4) plus flatten/take_while/zip, which do not derive at all.

## Execution engine — DBSP REMOVED, and what that did and did not buy

State on 08-02: MERGED to main as 2f97ada (PR #1). This section exists so the
next person does not re-derive the analysis or repeat the two dead ends.

DBSP was the declared engine, imported by 2 of 13 crates, 163 of 491 packages.
Neither use needed it, and they failed for OPPOSITE reasons. That is the whole
finding; everything else follows from it.

  infact-rust-effects::propagate_effects   RECURSIVE, ZERO DELTAS
    Built a circuit, pushed every call and seed, called transaction() once,
    dropped the circuit. transaction() appeared exactly once in the crate and
    no push ever carried a negative weight. The recursion was load-bearing,
    the incrementality was not. Now one ascent rule.

  infact-duplication::ExactEngine          INCREMENTAL, NOT RECURSIVE
    indexed.join(&indexed) is a group-by; no recursion anywhere in the crate.
    Retraction fires only when a path is replaced, which only two self-tests
    do. And ExactEngine is pub(crate) inside a private `mod engine`, so no
    consumer CAN reach the incremental API. Now a plain hash group-by.

Nothing used recursion and incrementality together, which is why one site
became Datalog and the other became no engine at all.

  The self-join emitted each unordered pair TWICE (both orders canonicalise to
  the same MatchSeed), which is the only reason the i64 weight ledger existed.
  A group-by emitting left<right once deletes the ledger and advance() rather
  than translating them. replace() semantics fall out of recomputing from the
  stored windows, so both retraction tests still pass UNCHANGED.

  rkyv, size-of and feldera-macros left with dbsp. They were in those two
  manifests only to satisfy five rkyv/SizeOf/IsNone derive stacks -- a symbol
  grep for `dbsp` does not show them.

### A bug this found, which is the part that mattered most

  infact-rust-errors::search_upward tangled four jobs in one loop, and its
  Sealed fallback reported whichever chain the traversal happened to build
  last rather than any property of the graph. Given a caller that reaches the
  discard BOTH directly and the long way round, it reported that callable as
  three calls away when it was one. It reported a walk and called it a
  distance.

  Now: classification and evidence reconstruction are separate steps over
  pathfinding::dijkstra_all, and the fallback is defined as the furthest
  caller BY SHORTEST ROUTE, ties broken on lowest index rather than on search
  order. Pinned by a_sealed_chain_is_measured_from_the_shortest_route, which
  FAILS against the old code.

### Do not re-attempt these. Both were built and measured, then reverted.

  REACH RESOLUTION AS DATALOG.  102 lines against 39. ascent has no
  provenance -- no proof trees, no derivation tracking -- so a Datalog version
  reconstructs by hand what a BFS yields for free on its way to the answer.
  Also: ascent's `lattice` codegen emits unwrap(), and this workspace denies
  clippy::unwrap_used. #[allow] on the macro invocation does NOT suppress it
  (rustc reports the attribute itself as unused); the only clean scope is a
  separate crate. The Dual<u32> distance-lattice technique DOES work and

  RELATION. Every other candidate produces a WITNESS -- a specific path with
  evidence spans, for a human-readable report -- and infact is an
  evidence-producing system by design (AGENTS.md: "Facts retain source spans
  and derivation provenance"). Datalog gives you what is true and discards why.

## TypeScript — the frontend, what was measured, and what was predicted wrong

Landed 08-02 in `infact-ts-normalize` plus three laws in the algebra. State:
25 of 155 annotated positives, 4 false positives against 252 annotated
negatives, reproducible from `tools/ts-scoreboard`. Nothing is wired into
`infact-analysis`; this is the frontend and the measurement, not the pipeline.

### The finding that reshaped the task

TypeScript's standard library has NO IMPLEMENTATIONS.

    lib.es5.d.ts          0 statement-like lines / 4599
    lib.es2015.core.d.ts  0 statement-like lines / 595

`Array.find` is a declaration and nothing else. The whole Rust approach derives
behaviors from std's SOURCE, and there is no equivalent to point at. npm
packages are fine — their source is in node_modules — but the builtins, which
are exactly what the reuse-shaped lints care about, have no body anywhere in the
TypeScript distribution. Everything below follows from that.

### Which engine, and why not the obvious ones

SpiderMonkey self-hosts 89 builtins in PLAIN JAVASCRIPT: Array.js 26,
String.js 35, Object.js 18, Map.js 6. It parses with the JavaScript grammar we
already ship, so it costs no new frontend.

  core-js       DISQUALIFIED STRUCTURALLY, not on taste. `internals/array-
                iteration.js` is one `createMethod(TYPE)` factory serving
                forEach/map/filter/some/every/find/findIndex behind an integer
                discriminator and a `switch (TYPE)`. Seven callables, one source
                function, one derived form, same container — the collision class
                `collisions.rs` exists to catch.
  V8            Torque, so a new grammar nobody maintains. And 4 of the 5
                functions in `array-find.tq` are TurboFan deopt plumbing; one
                has a body of `unreachable;`, which would derive to something
                that matches everything. Only `ArrayFindLoopContinuation` is the
                behavior. Not worth acquiring a grammar for.
  es-shims      MIT, one package per method, but `flatMap` delegates into
                es-abstract's `FlattenIntoArray` and `startsWith` is charCode
                arithmetic. Same optimizer-shaped dead end as `Vec::retain`.

MPL-2.0 is why the source is fetched into `<measure>/`, never vendored —
exactly as the Rust std pack derives from the local rustup toolchain. What
ships is the derived form plus spans and digests.

SpiderMonkey preprocesses its self-hosted JavaScript, so a few `#if`/`#endif`
lines are unreadable. Do NOT add a dialect rewrite for it: the damage is local,
tree-sitter recovers, and function counts match `grep` exactly. 89 top-level
functions, exactly 1 damaged (`ArrayToLocaleString`, not a reuse target).
`NormalizedFunction.damaged` declines it. A rewrite that blanked the directives
would leave BOTH branches and silently merge them.

### Direction has to live inside the traversal

`filter(p).pop()` is `findLast`, not `find`. Encoding that as a reversal
wrapped around the sequence DOES NOT WORK, and the reason is worth keeping: the
sequence sits exactly where a derived behavior has a hole, and a hole absorbs
anything, so the forward search matched backwards code and named the opposite
API. Measured — the negative test caught it. This is the `next`/`next_back`
bug reached from a new direction.

`Form::Traverse` therefore carries a `Direction`. A forward walk does not
serialize the field, so every behavior derived before it existed keeps its
digest; there is a test asserting the exact legacy bytes. Splitting `Traverse`
out of the arm it shared with Transform/Sift/Retain dropped a `fused_body`
fallback and broke `itertools::counts` — `infact-rust-behaviors`' corpus test
caught that, which is the second time that suite has paid for itself.

### Rust gets a free anchor that JavaScript does not

`is_reportable` requires `anchors() >= holes()`. Measured:

    ArrayFind      size=10 anchors=1 holes=2  reportable=FALSE
    ArraySome      size=10 anchors=2 holes=2  reportable=true
    ArrayForEach   size=7  anchors=1 holes=2  reportable=false  (correctly)

`find` failed by exactly one anchor, and structurally: Rust's `find` returns
`Option<T>` so its form carries `(variant Some p)` for free, while JavaScript
returns the bare element or `undefined`. Modelling `T | undefined` as the
optional it is restores the anchor AND converges the two languages on one form —
character-for-character the `find` shape this note already recorded for Rust.
That is the `optional-search` law. `some` does not collapse into it because
`some` yields a literal, not an absence.

### The corpus disagreed with the plan, twice

155 annotated positives across `prefer-find`, `prefer-includes` and
`prefer-array-find`. ZERO are loop-shaped. They are all chains — `filter(p)[0]`
— which is the same wall this note already records for Rust ("Fusion was going
to unlock the chains. It moved clippy by ZERO"). The hand-written loop that
Phase 0 proved works is a shape the corpus never asks for. Laws as they stood
scored 0/155 while every internal check reported success.

Second miss: gating matches on the observed receiver type collapsed recall
25 -> 6, because 452 of the receivers type as `any` — the snippets never declare
`array`. `any` means the checker established NOTHING, not "this is not an
array". Declining on it turns "not looked at" into a confident negative. Only a
KNOWN, non-array-like receiver declines. Typed arrays are array-like:
`Int8Array` is a true positive.

### What NOT to spend time on

  `prefer-includes` (29 positives). Wants `indexOf(x) !== -1` -> `includes`,
  which is a peephole identity about indexOf's contract, not "you reimplemented

  unicorn's adversarial spellings — `[fltr]` where `fltr` is a string const,
  ``[`at`]``, `.at(NaN)`, `filter(p)['0']`. Those test THEIR rule's edge
  handling. A behavior matcher should not resolve a computed member name to a

  `.pop()`/`.at(-1)` are 11 positives and they are `findLast`, which now derives

Realistic ceiling on the current corpus is around 100 of 155, not 155.

### Can TypeScript behaviors be packs? Yes, unchanged

Checked against `infact-fact-pack`: the model is already language-neutral.
`Subject { kind, language, ecosystem: Option<String>, name, version }` takes
`language = "typescript"`; `SubjectKind::Language` covers the standard library
and `Library` covers an npm package; `SourceKind::Repository` is exactly right
for pinning a gecko-dev revision by digest without vendoring it. Capabilities
are already namespaced by language, and `validate_runtime` derives
`typescript.syntax-tree` from the parser pack's own language id, which the
shipped TS pack declares. So:

    provides = ["typescript.callable-signatures", "typescript.library-behaviors"]
    requires = ["typescript.syntax-tree"]
    [subject] kind = "language", language = "typescript", name = "ecmascript"
    [[sources]] kind = "repository"   # gecko-dev, pinned by revision + sha256

No change to the pack format is needed. What is missing is the crate that builds
one.

TWO GAPS THE FIXTURE FOUND, both language-neutral:

  A call buried in an expression is not followed. `delegation_target` is a shape
  test over the WHOLE form, so `return indexOf(x) !== -1` — which is how
  `includes` is normally written — describes a comparison rather than a search.
  Rust has the same hole; `counts` is followed only because its body is exactly
  the call. Worth measuring before building: how many std callables are
  one-expression wrappers of this shape.

  A constructor function is not a type. `type_declarations` reads `class`,
  `interface` and `type`, so pre-class JavaScript — `function Foo() {}` plus
  `Foo.prototype.bar = ...` — declares nothing followable. Neither is
  `Array.prototype.find = function () {}` collected as a callable at all, nor
  `module.exports`. Those are the shapes an older npm package is written in, and
  they bound what this reaches on real dependencies far more than the laws do.

### Running it on a real project — pi.dev, 1,047 files, 238k lines

Everything above was measured against lint fixtures. Pointing it at a real
TypeScript monorepo changed what the open problems are. Recorded so nobody
re-derives it.

WHAT THE PROVIDER DID: 18 seconds, 1.9GB, 88,013 calls, 47,012 receiver types,
609 gaps (0.7%), every span repository-relative. Scale was the thing least
likely to hold and it held.

WHAT NEEDED FIXING, in the order the evidence forced it:

  1. PARSER SETUP, NOT MATCHING. A scan that would not finish in eleven minutes
     was 96% tree-sitter, and 78% of that was `runtime.load` being called once
     per file. `LoadedParser::parse` then rebuilt a `Parser`, a `WasmStore` and
     called `set_language` on every call: a 19-byte file took 123ms and a 40KB
     file took 210ms, so nearly all of the smaller number was setup. Fixed in
     entl (PR #7). This was never a TypeScript problem — `parse_repository`
     calls `parse` per file, so every analyzer paid it.

     Do NOT assume matching is the bottleneck. It was 3%.

  2. FOUR KINDS OF JAVASCRIPT WERE UNREADABLE. Named arrow functions (862 of
     pi's, a quarter of its named functions), counted `while` loops (45 of
     lodash's files), `reverse().find(p)`, and multi-declarator statements.
     Each was found by running against real code, none by reading the code.

  3. AN ANCHOR PREFILTER SKIPS 99.5% OF PAIRS. A pattern only matches a subject
     containing every name it states outright, so `subject ⊇ pattern` on the set
     of method names, constants, paths, variants, fields and operators is a
     necessary condition, and it is a set lookup rather than a tree walk. On a
     40x40 workload it removed 19,350 of 19,440 pairs at 0.001ms against
     0.093ms. Verified sound on a corpus: 97 findings with and without.

     STILL ONLY IN tools/. It belongs in infact-normalize beside `matches`, and
     infact-rust-behaviors runs the identical `for behavior in &reportable`
     loop, so the Rust pipeline gets the same win. Wanted first: a property test
     asserting the prefilter never rejects a pair `contains` accepts.

### The confounds, which cost more than the bugs

A WORKSPACE LINKS ITS OWN PACKAGES INTO node_modules. pi has
`node_modules/@earendil-works/pi-ai -> ../../packages/ai`. Deriving a library
from node_modules therefore derives the project, and then reports the project
for reimplementing itself: 795 findings, nearly all self-matches. Canonicalizing
both sides and dropping anything that resolves back inside the project takes it
to 5. This is not a pi quirk — every npm/pnpm/yarn workspace does it.

A DELIBERATE FORK IS NOT A FINDING. `coding-agent/src/core` is a copy of
`agent/src/harness` on purpose. Suppression has to be by LOCATION, not by file:
fold the mirrored prefixes to one place, and a finding living entirely inside
them counts once and drops, while a finding that also appears outside keeps its
second location and stays. 23 findings suppressed, and `findLastIndex` — which
appears twice inside the fork and once outside — correctly survived.

### What pi actually has, and what that says about the premise

  93   `error instanceof Error ? error.message : String(error)`, no helper
       anywhere in the repository. 22 files, 41 sites at function granularity.
       `runner.ts` writes it eight times in eight adjacent methods.
   6   `message.content.filter(b => b.type === "text").map(b => b.text)` under
       six different names in four packages.
   5   a filter for tool-call content
   3   a hand-rolled `findLastIndex`

NONE of these is lint-shaped. pi runs Biome 2.3.5 with `recommended: true` and
`--error-on-warnings` in CI, and it PASSES on every file above. Biome has no
`findLast` rule and no `includes` rule at all. Two of the four are not
single-file questions in principle: the error ternary is correct code at all 93

THE ORIGINAL PREMISE DID NOT FIRE. "You hand-wrote what a library already does"
found 5 things across 2,669 behaviors derived from pi's own dependencies, and

What DOES fire on a real codebase is the repository against ITSELF. That is a
different entry point from `library-opportunity` and on this evidence the more
valuable one.

### Two thresholds, not one

Big-and-repeated finds copied code. Small-and-everywhere finds a missing word in
the project's vocabulary. One setting can only ever see one of them — ranking by
`count x size` buried the error ternary under the compaction clones, and a
7-node floor with the `is_comparable` gate excluded it outright, because a
ternary over `instanceof` is neither a traversal nor a decision.

The split that works: a form containing a branch, traversal, method or call is a
candidate abstraction; a bare comparison is an idiom. Idioms are reported and
labelled as NOT defects, because `xs.length > 0` in 73 files is how the language
is written.

Thresholds are 7 nodes / 4 files and 4 nodes / 10 files, calibrated against ONE
repository. Moving the file cutoff from 4 to 3 changed the result set
substantially. Treat the ranking as a hint.

## Reading the files that were being thrown away — 08-04

`parse_repository` discards any file whose tree has an error, WHOLE. Found while
building the TypeScript frontend, where three of SpiderMonkey's four files carry
`#if` preprocessor lines and discarding them left 18 callables out of 89. Then
measured on Rust, where nobody had looked.

### What was hidden

    core                31 unread files, holding 1,363 functions

Among them `cmp.rs` (136 fns), `fmt/mod.rs` (160), `slice/index.rs` (94),
`str/pattern.rs` (81), `ptr/mod.rs` (58), `sync/atomic.rs` (112). Everything
they define was missing from the std pack, and `--allow-unread` is what turned
that into a warning rather than a stop. The failure looks exactly like a library
that simply has less in it.

It also poisoned a tally this note leans on: a callable whose implementation sat
in a discarded file is INDISTINGUISHABLE from one with no implementation
anywhere, so part of item 4's 1,332 was never a coverage question at all.

### The fix, and what it is not

Read the file anyway; decline the functions whose own subtree carries an error,
BY NAME. Tree-sitter recovers locally, so the damage is bounded to the construct
that caused it: across core+alloc+std, 22 functions were actually damaged where
31 whole files were being dropped.

NOT a dialect rewrite. Blanking the directives leaves BOTH branches of a
conditional in place and silently merges them, which is the erasure class this
project keeps paying for. The existing dialect table is for syntax that can be
neutralised without moving a byte; `#if` is not that.

## A behavior is language-neutral; a MATCH is not — 08-04

`FactPackSet::load` flattened every pack's behaviors into one list and handed
that list to `infact-rust-behaviors`. Which pack a behavior came from — and so
which language it was derived from — was dropped at load.

That was harmless while only Rust packs existed and stops being harmless the
moment a TypeScript pack does. A `Form` names no language, which is the entire
point of it: a search derived from JavaScript matches a Rust function of the
same shape perfectly well. The finding would name an ECMAScript builtin at a
Rust call site, and nothing in the output would say anything was wrong. Same
failure class as every entry in the collision section — a distinction erased
somewhere upstream, invisible where it lands.

`FactPackSet` now keeps each behavior with `manifest.subject.language`, and each
frontend is offered only its own. Asserted by
`behaviors_are_only_offered_to_the_language_they_came_from`, which uses the
itertools pack rather than the core one on purpose: core is the EFFECTS pack and
carries no library behaviors at all, so the test would have passed by finding
nothing on either side. The test says so in a comment, because that is exactly
the shape of a test that measures nothing.

TypeScript is now wired into `analyze_repository` beside Rust, so a repository
scan reports TypeScript reuse through the ordinary path rather than only through
`tools/ts-scoreboard`. It parses the repository a second time and is skipped
entirely when no pack describes TypeScript.

[ ] The two frontends parse the repository once each. One walk feeding both
    would halve that, and needs `parse_repository` to hand back files grouped by
    language rather than each analyzer filtering the whole set.
