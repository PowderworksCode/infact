## Resolved-destination allocation (clone/to_owned by receiver type)

State on 08-02: WORKING AND TESTED, NOTHING COMMITTED. Read the transfer
section at the bottom FIRST — most of this exists only in a working tree.

The question was whether the MIR provider could supply the receiver types that
`clone` and `to_owned` need. It can, but not as it was written, and the change
that makes it work also breaks something silently. All three parts below are
one change; landing part 1 without part 2 is a regression that reports success.

### What was measured, so nobody re-derives it

Probed the driver against a fixture of clone/to_owned/collect/format calls.

  BEFORE. Every clone collapses to one destination:
    clone_an_arc     -> std::clone::Clone::clone
    clone_a_string   -> std::clone::Clone::clone
    clone_a_vec      -> std::clone::Clone::clone
    own_a_str        -> std::borrow::ToOwned::to_owned
    own_an_integer   -> std::borrow::ToOwned::to_owned
  The receiver is discarded at the `RigidTy::FnDef(def, _)` match — the `_` is
  the generic args, which is where `Self` lives — and `def.0.name()` names the
  trait method rather than the impl. `coverage.types` is false and `types` is
  empty; that part is honest and unchanged.

  AFTER `Instance::resolve(def, &args)`:
    <std::sync::Arc<std::string::String> as std::clone::Clone>::clone
    <std::string::String as std::clone::Clone>::clone
    std::str::<impl std::borrow::ToOwned for str>::to_owned
    <i32 as std::borrow::ToOwned>::to_owned
    <Copied<Iter<'_, u8>> as Iterator>::collect::<std::vec::Vec<u8>>
    std::vec::Vec::<u8>::with_capacity
    std::fmt::format
  More than asked for: `collect`'s TARGET container is in the name, and
  `format!` arrives as an ordinary resolved call to `std::fmt::format`.

  `i32::clone` emits NO call terminator at all — inlined away. Do not rely on
  that to filter Copy types: `i32::to_owned` DOES emit one.

### The trap, and it is the important part

Resolution rewrites `std::fs::read` to `std::fs::read::<&str>`. Every catalog
lookup is an exact map `get`, so all of them stop matching. Measured: with the
regenerated fixture and no other change, 5 of 6 `observed` tests failed with
empty effect sets while the run still reported `EffectResolution::Observed`.
The one test that PASSED was `a_pure_function_reports_no_effect`. A confident,
empty answer is the worst failure this codebase can produce, and it is what
part 1 alone produces.

### Two parsing traps found the hard way, both now regression-tested

  `::<impl Trait for Type>` opens exactly like a turbofish. Stripping it as one
  discards the receiver — the single thing the resolved destination was wanted
  for. `path::without_turbofish` special-cases it.

  A resolved `collect` arrives QUALIFIED (`<Iter as Iterator>::collect::<..>`),
  so a `collect` branch written in the unqualified arm never fires. Order
  matters in `allocating_destination`: check `collect` before the qualified-self
  branch.

### Decided, with the reason, so it is not relitigated

  The seed's `origin` records the DECLARED catalog path, not the resolved
  instance. Otherwise one catalogued API gets a different origin at every call
  site that instantiates it differently, which fragments any grouping a
  consumer does. `external_effect` returns the matched key for this.

  `clone`/`to_owned` are decided ONLY on the observed path. The syntax path
  still declines them outright and must keep doing so — it has no receiver
  type and a guess would put false origins in the one relation whose value is
  that it can be trusted.

  User types are declined for `clone`. A custom `Clone` may do anything.

  The name-based tables were kept as the fallback rather than replaced.
  `allocating_destination` defers to `allocating_call` for anything it cannot
  place, and the syntax path still needs them.

### Result, same seven functions through both paths

  syntax                          observed (MIR)
    collects_a_vec   collect        clones_a_string  String::clone      NEW
    collects_nothing collect  <-!   collects_a_vec   collect::<Vec>
    formats          format!        formats          std::fmt::format
                                    owns_a_str       str::to_owned      NEW
                                    (collects_nothing absent — correct)

  Two allocations that were invisible; one false positive gone
  (`Result<(), ()>` collects nothing); `Arc::clone` still correctly declined,
  which is the discrimination and not merely more hits.

## Behavior derivation — the algebra, decisions, and candidate sets

State on 08-02: WORKING AND TESTED, NOTHING COMMITTED. Separate thread from the
allocation work above; the two touch different crates and do not conflict.

The question was whether a library's behavior can be recognized in code that
reimplements it, for any library, without running anything. It can. `find` now
matches a hand-written loop, derived from std's source alone — no execution
anywhere in the pipeline, and rustc's own inliner and LLVM both fail to relate
those two, so this is not something a compiler was going to hand us.

### What was measured, so nobody re-derives it

Three corpora, all reproducible (commands at the bottom):

  std behaviors        290 -> 483    (a peak of 1,590 was mostly garbage; see below)
  clippy recall        0/201 -> 14/201, and 22 of 22 reported are on-target
  dependency corpus    34 -> 1,035 findings over 494 crates
  undecided matches    76 -> 64

The behavior count going DOWN from 1,590 to 483 was the point, not a loss. The
permissive gate admitted opaque `match` trees and `Arc`/`HashMap` methods
resolved to unrelated functions; removing them cost no recall on either corpus.

### The one idea

Each law is an equivalence that holds in the LANGUAGE, not in any library, so
one set serves every library there is. In crates/infact-normalize/src/simplify.rs:

  unfolding       a name bound to a body is that body
  traversal       a fold whose accumulator is unused is a traversal
  escape          breaking out of a fold is returning from a loop
  recovery        asking a fold for the value it broke with is that return
  generalization  a name nothing in the form binds is a hole
  fusion          mapping what was filtered is one pass, not two

These five unlocked NINE std methods at once — find, find_map, try_find, any,
all, position, for_each, try_for_each, partition — because all of them are
written with try_fold + ControlFlow. That is the evidence that the approach is
about the language and not about `find`.

Matching gained one rule of the same kind: a hole APPLIED to a bound name
matches any expression over that name (Miller pattern unification). That is
what lets a library's `predicate(item)` match a caller's `item == target`.

### The recurring bug, which is the important part

Eight distinct bugs this session were ONE pattern: a distinction erased in
normalization. Each produced hundreds to thousands of confidently wrong
findings, and none was visible in the output.

  true / ()                 both were Form::Literal. 1,390 false matches.
  map / filter_map          one TRANSFORM_METHODS list. map cannot drop.
  next / next_back          ranked by size, so the reverse iterator won.
  e.into() / e              stripped as noise. into_ok became into_err.
  Self                      read as a type name. 55 behaviors from non-bodies.
  (k, _) / (_, v)           `_` is anonymous, so the position was dropped.
                            BTreeMap::keys and ::values were one behavior.
  arm order                 `match` survived as syntax, so order was behavior.
  filename collisions       {package}-{leaf}.json. 23% of every pack overwritten.

FOUR of these were found by accident. The last four were found on purpose, by
crates/infact-rust-behaviors/tests/collisions.rs, which asserts that distinct
callables derive distinct forms. RUN THAT FIRST after any normalizer change.
It is the cheapest bug detector in the project.

3. LAZY-ADAPTOR DERIVATION. THE LIFT IS BUILT AND CORRECT. IT MOVED CLIPPY BY
   ZERO. That is the FIFTH misprediction in a row, and this time the laws were
   right and the reach was wrong again — read the warning below before doing
   anything with the rest of this item.

   BUILT 08-02, `Form::lifted_from_one_step` in infact-normalize/src/simplify.rs:
     core::Iterator::filter_map  ->  (sift f0 v1 (call f1 v1))
   exactly the form this item predicted. `find_map` correctly did NOT lift and
   keeps its search form, which resolved the filter_map/find_map collision
   (same-container collisions 10 -> 9). The lift is deliberately NOT a law and
   is not part of `simplify`: a search stops at the first hit and a lazy adaptor
   does not, so only derivation may apply it.

   The licence is STICKY, and this is the part that is easy to get wrong. The
   construction is followed at `filter_map -> next`, but the liftable form only
   appears one step LATER, at `next -> find_map` via ordinary delegation. A
   per-step flag reads false exactly where the lift is needed. Derivation tracks
   `inside_one_step` across the whole walk and lifts once at the end.

   The stateful guard is in and fails closed (`is_stateful_step`): refuses a
   step that assigns through a field or walks more than one sequence.

   WHY IT SCORED NOTHING, measured on one case rather than guessed. The two
   sides do not meet:

     library, after the lift   (sift f0 v1 (call f1 v1))
     user, .filter(p).map(f)   (collect (sift f0 v0 (branch COND (Some ..) (None))))
     user, the manual loop     does not reduce to a sift AT ALL — it stays
                               (do (let v0 (construct Vec))
                                   (traverse f0 v1 (select .. => (method push v0 v2)))
                                   v0)

   So fusion does produce a `Sift` from a chain, but its body is an explicit
   Option construction where the library's is a bare applied hole, and the whole
   thing sits under a `collect` the library form has no counterpart for. The
   claim in this note that `(sift f0 v1 (call f1 v1))` "matches BOTH
   .filter_map(f) and the fused .filter(p).map(f)" was hand-verified and is
   WRONG as measured: zero findings on the probe.

   THE BLOCKER IS `is_reportable`, AND IT IS NOT A BUG. Chased 08-02 and the
   first two guesses were both wrong; recorded so nobody re-walks them:

     WRONG GUESS 1: the `collect` wrapper. Disproved by probing the same chain
     WITHOUT a collect — `(sift f0 v0 (branch ..))` bare still does not match.
     `search` already recurses into children, so the wrapper was never in the
     way.
     WRONG GUESS 2: `(call HOLE item)` failing to match `(branch ..)`.
     `abstraction` implements exactly that (Miller unification) and none of its
     refusal conditions fire here.

   THE ACTUAL REASON. `is_reportable` demands `anchors >= 2` AND
   `anchors >= holes`. The lifted form is

       (sift f0 v1 (call f1 v1))     anchors 0, holes 2

   `Sift`, `Free`, `Call` and `Local` all contribute NO anchors. It names no
   type, no method, no operator, no constant — it is pure shape, and pure shape
   matches any code of that shape. That is the `Option::map_or` failure this
   codebase already paid for once: technically right, reported nine hundred
   times across five hundred crates, useless. Asserted now by
   `the_lifted_form_names_nothing` in simplify.rs so it is not rediscovered.

   NOTE THE TRADE. Before the lift, `filter_map` carried the big
   Sequence/Traverse/Select form, whose `Select` arms name `Some` and `None` and
   so DOES clear the anchor bar. The lift exchanged a reportable-but-ambiguous
   form (identical to `find_map`, so any match named the wrong API half the
   time) for an unambiguous-but-unreportable one. Neither scored: recall was
   14/201 before and after. Precision went up, reportability went to zero.

   SO THE ~63 POINTS ARE NOT REACHABLE THIS WAY AT ALL, and the reason is the
   one already written in "What NOT to spend time on" below. manual_filter_map,
   manual_find_map and filter_map_next are SHAPE lints, exactly like
   needless_range_loop and manual_while_let_some: `filter_map` names nothing, so
   "you could use filter_map" is a statement about shape and not about
   reimplementing a particular library function. Getting them requires weakening
   `anchors`, which exists for a measured reason. That is the same trade this
   note already declined once, and the ~63 belongs in the NOT-worth-it list
   rather than in this item's headline.

   WHAT THE LIFT IS STILL WORTH. It is correct, it is tested, and it resolved
   the filter_map/find_map collision. Keep it. Its value is precision, not
   recall, and this item should no longer be sold on a clippy number.

   ORIGINAL NOTE FOLLOWS, kept because the analysis of the lift itself held up.

   Phase 0 is DONE and the premise holds. A lazy
   adaptor's behavior derived from `next` is ONE-STEP semantics: FilterMap::next
   delegates to find_map, so what is stored under `filter_map` IS find_map. The
   lift is one rewrite — a terminal search is the lazy operation with a stop in
   it, so drop the stop:

     (do (traverse s x (select SCRUT (None) => (lit) (Some p) => (return (variant Some p)))) (variant None))
       -> Sift(s, x, SCRUT)
     (do (traverse s x (branch COND (return (variant Some x)))) (variant None))
       -> Retain(s, x, COND)

   Verified by hand that `(sift f0 v1 (call f1 v1))` then matches BOTH
   `.filter_map(f)` and the fused `.filter(p).map(f)`.

   License it only on the ONE branch in derivation.rs where a callable merely
   constructs a type and we follow into its principal method. That branch is now
   exactly the lazy-adaptor path — the `principal.then_some(..)` fix removed
   Arc and HashMap from it, so it needs no further guarding against them.

   Guard it against STATEFUL adaptors, failing closed: refuse when `next`
   mutates self fields, touches more than one sequence, or loops. Flatten,
   Peekable and Chunks must refuse; they do not derive today, so refusing costs
   nothing and admitting them would be undetectable downstream.

   Worth ~63 clippy points (manual_filter_map 29, manual_find_map 30,
   filter_map_next 4) plus flatten/take_while/zip, which do not derive at all.

4. THE 1,332 "no implementation was found" CALLABLES. A third of std, never
   looked at. `infact behavior library --explain` reports the tally. Measure
   before guessing — see the warning below.

### What NOT to spend time on

  Vec::retain (38 clippy points), str::strip_prefix, str::split_once. std's
  implementations are optimizer-shaped — BackshiftOnDrop with raw pointers, or
  the work lives in Pattern/Searcher trait impls rather than the named callable.
  Confirmed three ways earlier: the source does not resemble user code, MIR will
  not inline try_fold, LLVM unrolls the two forms differently. These need a
  different mechanism, not more laws.

  needless_range_loop, manual_while_let_some. Real clippy lints, but not "you
  reimplemented a library function". Chasing them makes us a worse clippy
  instead of the thing that works on any dependency.

  A table of adaptor name -> operation. It would work and it is exactly the
  per-library knowledge the design exists to avoid.

### A warning about predictions

I mispredicted the blocker FOUR times in a row, and each time the corpus said
something different from what the reasoning said:

  `if let` was going to unlock find_map/filter_map/flatten. It unlocked none —
  those tests are method CHAINS, and Iterator::flatten is a FlattenCompat state
  machine that does not derive at all.
  Fusion was going to unlock the chains. It moved clippy by ZERO, because of the
  one-step semantics in item 3.

The laws have been right every time; the model of what they would REACH has not.
Measure a hypothesis on one case before building for it. Phase 0 above is what
that looks like and it took one command.

## Execution engine — DBSP REMOVED, and what that did and did not buy

State on 08-02: MERGED to main as 2f97ada (PR #1). This section exists so the
next person does not re-derive the analysis or repeat the two dead ends.

DBSP was the declared engine, imported by 2 of 13 crates, 163 of 491 packages.
Neither use needed it, and they failed for OPPOSITE reasons. That is the whole
finding; everything else follows from it.

  infact-rust-effects::propagate_effects   RECURSIVE, ZERO DELTAS
    Built a circuit, pushed every call and seed, called transaction() once,
    dropped the circuit. transaction() appeared exactly once in the crate and
    no push ever carried a negative weight. The recursion was load-bearing,
    the incrementality was not. Now one ascent rule.

  infact-duplication::ExactEngine          INCREMENTAL, NOT RECURSIVE
    indexed.join(&indexed) is a group-by; no recursion anywhere in the crate.
    Retraction fires only when a path is replaced, which only two self-tests
    do. And ExactEngine is pub(crate) inside a private `mod engine`, so no
    consumer CAN reach the incremental API. Now a plain hash group-by.

Nothing used recursion and incrementality together, which is why one site
became Datalog and the other became no engine at all.

  The self-join emitted each unordered pair TWICE (both orders canonicalise to
  the same MatchSeed), which is the only reason the i64 weight ledger existed.
  A group-by emitting left<right once deletes the ledger and advance() rather
  than translating them. replace() semantics fall out of recomputing from the
  stored windows, so both retraction tests still pass UNCHANGED.

  rkyv, size-of and feldera-macros left with dbsp. They were in those two
  manifests only to satisfy five rkyv/SizeOf/IsNone derive stacks -- a symbol
  grep for `dbsp` does not show them.

### A bug this found, which is the part that mattered most

  infact-rust-errors::search_upward tangled four jobs in one loop, and its
  Sealed fallback reported whichever chain the traversal happened to build
  last rather than any property of the graph. Given a caller that reaches the
  discard BOTH directly and the long way round, it reported that callable as
  three calls away when it was one. It reported a walk and called it a
  distance.

  Now: classification and evidence reconstruction are separate steps over
  pathfinding::dijkstra_all, and the fallback is defined as the furthest
  caller BY SHORTEST ROUTE, ties broken on lowest index rather than on search
  order. Pinned by a_sealed_chain_is_measured_from_the_shortest_route, which
  FAILS against the old code.

### Do not re-attempt these. Both were built and measured, then reverted.

  REACH RESOLUTION AS DATALOG.  102 lines against 39. ascent has no
  provenance -- no proof trees, no derivation tracking -- so a Datalog version
  reconstructs by hand what a BFS yields for free on its way to the answer.
  Also: ascent's `lattice` codegen emits unwrap(), and this workspace denies
  clippy::unwrap_used. #[allow] on the macro invocation does NOT suppress it
  (rustc reports the attribute itself as unused); the only clean scope is a
  separate crate. The Dual<u32> distance-lattice technique DOES work and
  terminates on cycles -- proved in ascent-probe/src/reach.rs -- it just costs
  more than it saves here.

  evidence_path VIA pathfinding::bfs.  52 lines -> 64. Semantically fine, and
  the original has no bug, so it bought nothing.

  The general rule that predicts both: ascent belongs where the OUTPUT IS A
  RELATION. Every other candidate produces a WITNESS -- a specific path with
  evidence spans, for a human-readable report -- and infact is an
  evidence-producing system by design (AGENTS.md: "Facts retain source spans
  and derivation provenance"). Datalog gives you what is true and discards why.
